GENERAL GUIDE — DESIGN KIT
Updated: October 8, 2026.

PURPOSE
Iterate with GENERATED IMAGES of any visual unit: text, icon, button, component,
family, section or whole page. A final coded/editable design is NOT created by
the kit. The user chooses the scope, visual acceptance and stopping point.

DEFAULT FOR MULTI-PART WORK
1. Use the user's foundation or a clearly provisional kit-proposed visual
   direction, grounded in actual inspected Awwwards / One Page Love MCP
   references where useful.
2. Choose a high-leverage FIRST COMPONENT or typography element. Generate
   and revise its image until the desired style is selected.
3. Reuse that actual component image and foundation for related components.
   When the shared style stabilizes, GENERATE COMPONENT GROUPS IN BATCHES.
4. Inspect and refine the visual component library for consistency.
   The USER or Design Kit can make those image refinements.
5. When requested, compose SECTION IMAGES from the accepted components,
   then more sections. Optionally review the complete page's images together.
6. STOP whenever the user wants: one word/element, component, group, library,
   section or full page. A smaller request does NOT require a larger workflow.

PHASED IMPROVEMENT INSIDE EACH IMAGE UNIT (NOT INSTEAD OF COMPONENT-FIRST)
Use PHASED_REFINEMENT.md on a word, component, family, section or page:
  Phase 1: fundamental concept/visual implementation: copy, proportion,
           hierarchy, size, base type/color, radius and shape.
  Phase 2: precision/craft: optical alignment, stroke, controlled gradients,
           surface detail, image/crop and family consistency.
  Phase 3: advanced finish only IF it adds value: shadow, material, lighting,
           highlight, texture, visual depth. Skip for deliberate flat/minimal UI.
  Phase 4: user/contextual review of the best candidate and prior anchors.
Return to an earlier phase for an unsolved foundational problem; do not mask
bad proportions with effects. Phase 4 is a review, NOT a mandatory generation.
All phases share the current image unit and accepted style/library references.

MANDATORY FEEDBACK AFTER EVERY IMAGE ROUND OR RETURNED BATCH
Present the actual image result, compare material differences, and ASK what
the user wants next: revise, accept, change direction, generate matching
components, advance to sections or stop. Do not silently start another round.
Continue for as many user-requested rounds as tools/budgets permit. There is
no fixed two-pass ceiling.

MCP REFERENCES AND EFFICIENCY
Preserve working Awwwards / One Page Love integrations, curated REFERENCES.md
and reference helper. Actually INSPECT source imagery before using it. Reuse
accepted sources and chosen component images across descendants. Do not
automatically browse both providers or rediscover settled visual decisions.
Component-first reuse and batching may improve efficiency; token savings are
not established without measured tasks.

EXAMPLES
"Improve only this headline through images."
"Iterate on this control until I select it, asking me after every round."
"Match these three components to my accepted first-component image."
"Revise this entire existing design image directly."
No forced page or component library for a one-off request.

OPTIONAL SKILLS AND HONESTY
Third-party skills are optional authorized experiments, not guaranteed gains.
Generated text may be wrong; retain exact copy separately. Static image
specimens do not prove functionality or responsive implementation.
Keep actual results, reference provenance and user choices in the target record.
Canonical: SKILL.md, IMAGE_WORKFLOW.md, COMPONENT_LIBRARY.md.
