DESIGN FROM SCRATCH — DESIGN KIT
Updated: October 5, 2026.

START IN YOUR INTERFACE
Activate Design Kit in Codex app, Claude Desktop Code or Google Antigravity.
HOSTS.md covers setup and additional surfaces. You need not operate a CLI.
Prompt:
"Use Design Kit for [site/app/flow/section/component].
Product: [what it does and whom it serves]. Goal: [user task/result].
Constraints: [content, stack, brand, scope]. Ask for missing material inputs,
show references and a visual system before dependent construction.
Requested deliverable: [design only / frontend with QA]."

1. CONTEXT AND EXPERIENCE
Inspect the actual base, instructions and supplied inputs first.
Clarify only material audience, task, content, hierarchy and state gaps.
Show a useful summary/sketch and review its open decisions.
Do not invent user research or require a complete questionnaire.

2. VIBE AND FAITHFUL PROMPT EXPANSION
Reuse stated direction. Otherwise offer contextual options, surprise me and
free text. Translate the intended character into observable relationships.
Expand the sparse request into a useful brief/prompt under PROMPT.md.
Separate sourced facts/requirements, proposed interpretations and unknowns.
Preserve what the designer wants to avoid. Do not invent audience, features,
metrics or exact approved styles. Review this in the same vibe checkpoint.

3. REFERENCES
Match the deliverable/pattern and agreed aesthetic together across industries.
Business terms are optional filters, not automatic tags. A UI-library request
needs system/component evidence; a source's task fit cannot excuse a wrong aesthetic.
Inspect supplied examples as discovery seeds; reuse accepted evidence directly
for faithful implementation or fully specified local work.
Start with the selected MCP best suited to the question; use the other for a gap.
Then search relevant public catalog sources directly when MCPs do not resolve it.
If usable coverage is exhausted, explain the gap and invite user references.
Curate 4–8 strong, distinct, inspected initial references unless asked otherwise.
If fewer than four fit, continue eligible retrieval or disclose incomplete coverage
when access/budget is exhausted. Do not pad the selection with weak matches.
Show readable visuals, exact provenance, fit, contributions and exclusions.
Review selection/contributions, then ask whether to search further or continue.
Reuse an advance/refine choice already supplied with acceptance. Revise within
eight active references; wait for accepted interpretation and search closure.

4. SCOPED VISUAL SYSTEM
Reuse an existing system or propose missing foundations from accepted evidence.
Apply affected CRAFT.md criteria to real type styles, semantic color/state roles,
spacing/geometry, assets and relevant behavior. Keep a compact visual contract in
the existing target record. Preserve canonical values/paths; DESIGN.md records usage.
Explore selected originals' relevant subpages, patterns/states and available
public CSS/DOM or published token/component sources under REFERENCE_ROUTER.md.
Check coverage of needed system rules; deepen accepted sources for gaps, then
search focused supplements if necessary. Review new contributions and revise
rejected ones before dependent work; reuse prior acceptance and the agreed vibe.
Normalize contributions into consistent product roles/rules, not mixed identities.
Render applied roles and related variants/states at useful widths; inspect actual
properties/bindings and consumers, not merely a JSON/color list or one correct tile.
Review/correct until accepted before styled interface construction.
Public extracted styles are partial evidence, not a site's complete internal system.

5. COMPONENTS AND INTERFACES
Build only needed pieces/patterns, with representative content and relevant states.
A hero-only request does not authorize a full site or exhaustive component library.
Compose within scope, inspect the actual result and show the contribution.
Correct affected work and retain the stronger baseline. Section-by-section work
reuses accepted system/relationships instead of restarting each time.

6. REQUESTED FRONTEND AND QA
An initial frontend request authorizes implementation after design checkpoints.
Reuse useful HTML/CSS/tokens, integrate in the target stack and verify behavior.
Inspect relevant responsive states, fonts/assets, keyboard/focus and required checks.
Design-only stops at design; backend/database/infrastructure remain outside scope.
New setup/dependencies and publication follow actual existing authorization.

CONTINUITY AND EFFICIENCY
Retain accepted revisions, pending feedback and the next action in the existing
target record. Reuse provider schemas/results/captures and plan filters before
calls. Additional retrieval must answer an open question; honor quotas/budgets.
SKILL.md/ONBOARDING.md govern the flow; README.md/HOSTS.md/PROVIDERS.md explain
setup and limits. Tests do not establish aesthetic quality or model compliance.
