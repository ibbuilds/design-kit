FRONTEND IMPLEMENTATION AND QA — DESIGN KIT
Updated: October 6, 2026.

SOFTWARE.md is the implementation reference; SKILL.md owns scope and review.
For a delegated coded-design assignment, visual authoring and relevant frontend
verification happen in the same unit. A separate design-approval ceremony is not
required before writing the candidate. Preserve explicit reserved checkpoints.

Reuse the accepted code, components, tokens and assets instead of reconstructing
them from screenshots or aesthetic prose. Preserve behavior, public interfaces,
existing API contracts and human edits. When visual design is already resolved,
implement faithfully rather than reopening references or identity.

Inspect only relevant callers, states and checks. Use existing preview/test tools;
no dependency installation or new architecture by default. Exercise meaningful
loading, empty, error, disabled and successful states when applicable. Inspect
actual fonts/assets, responsive containers, content stress, keyboard/focus and the
requested task. Stills and a successful build do not certify live interactions.

Group repairs by their owner. Do not weaken tests or hide defects to pass. Respect
the global task budget; verification problems cannot become unlimited uncounted
work. Exhaustion means report incomplete scope and stop, not declare readiness.

For broad visual changes, preserve the accepted candidate during propagation and
check a contrasting consumer. Keep implemented, verified and human-accepted states
separate. Label mocks and untested services. Backend, database, infrastructure,
publication and private uploads are outside scope without separate authorization.
