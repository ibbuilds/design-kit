WORKFLOW 1 — DISEÑO UI + UX DESDE CERO
MANUAL PERSONAL PARA CREAR UNA INTERFAZ EXCEPCIONAL CON DESIGN KIT
Actualizado: 30 de septiembre de 2026.

OBJETIVO Y REPARTO DEL TRABAJO

El resultado buscado es un diseño hermoso, con carácter propio y una experiencia
coherente. Design Kit guía al agente que tú elijas para desarrollar tu criterio
y tu base. No es otra app ni un diseñador autónomo. El agente debe producir
trabajo visual que puedas juzgar, no informes que expliquen por qué es excelente.

Tú aportas conocimiento del producto, dirección, selección y foundations; puedes
delegar decisiones abiertas expresamente. El agente procesa el contexto, ayuda a
resolver estructura e interacción, busca referencias cuando lo pides, desarrolla
el sistema y compone/refina las páginas. Tú revisas cada fase o batch significativo.
Una corrección mantiene el batch abierto; una aceptación se reutiliza en su alcance.

El proceso cubre contexto/problema -> estructura de experiencia -> dirección y
referencias -> foundations -> componentes y patrones -> páginas y refinamiento
-> entrega de diseño. Código solo si lo solicitas. No es una cascada rígida:
una composición puede revelar una mejora en un componente o en la estructura.
Se vuelve a esa decisión, sin rehacer lo demás ni cambiar bases aprobadas en secreto.

El agente se encarga del QA pertinente antes de mostrar cada batch; no tienes
que ejecutar su checklist. QA ayuda a corregir problemas, pero no demuestra
belleza. Compliance, analítica, deployment y documentación empresarial no son
la finalidad ni etapas obligatorias de este flujo. La inclusión, claridad y estados
sí forman parte del diseño de la experiencia. No hace falta pagar otra herramienta.

1. ARRANCA EN EL PROYECTO CORRECTO

Carga Design Kit con tu agente. En Codex, una instalación local se hace con:
python "C:/ruta/design-kit/scripts/install.py" "C:/ruta/tu-proyecto"

Esto copia instrucciones/recursos a .agents/skills/design-kit/ y añade un pointer
en las instrucciones del proyecto. No instala Penpot, MCPs ni dependencias.
Para actualizar una instalación no modificada, ejecuta de nuevo el mismo script.
Otros agentes usan su mecanismo de skills o una petición explícita de leer SKILL.md.
Una carpeta presente no demuestra que el agente realmente haya cargado el skill.

En tu proyecto puedes decir:
"$design-kit Inicia el diseño UI/UX. Usa lo que ya aporté, dime la fase actual y
pide solo lo necesario. Quiero una dirección específica para este producto, no
un layout genérico. Presenta cada entrega y espera mi revisión antes de expandir."

No pegues este manual completo por rutina. Es para que tú entiendas el proceso.
El agente usa SKILL.md, el contrato/checkpoint y solo la fase/recurso pertinente.

2. PROPORCIONA CONTEXTO Y DEFINE QUÉ SE VA A DISEÑAR

Da un brief legible, un Notion con acceso, TXT/MD/PDF o respuestas en conversación.
Puedes poner un MD en .design/brand.md dentro del proyecto; no es obligatorio.
El agente debe mostrarte la ruta real si solicita un archivo. Si no puede acceder
al enlace, utiliza export o texto; no supone que el MCP existe por tener una URL.

Información útil: qué hace la marca/producto, por qué importa, público, necesidad
y tarea principal; qué debe comprender/hacer la persona; valores/voz/diferencia;
contenido y assets disponibles; alcance, dispositivos y restricciones relevantes.
Si ya hay evidencia o feedback de usuarios, compártelo. Si solo hay una hipótesis,
se identifica como hipótesis; no se inventan personas, estudios ni testimonios.

El agente resume lo comprendido, separando hechos, implicaciones y dudas materiales.
Revisa esa interpretación. El summary no crea un logo ni decide tipografías/colores.
No necesitas un PRD completo ni responder un cuestionario de investigación para
una pantalla sencilla. Las preguntas deben cambiar una decisión necesaria ahora.

SALIDA: contexto y problema de diseño entendidos, alcance y decisiones abiertas.
Tu confirmación desbloquea el trabajo dependiente.

3. RESUELVE LA EXPERIENCIA ANTES DE MULTIPLICAR PANTALLAS

La experiencia no aparece automáticamente porque tengas botones bonitos.
Hay que decidir qué contenido/acciones existen, su prioridad, cómo se agrupan,
qué términos usa la persona, cómo se orienta y qué ocurre al actuar.

Para una web de marca: qué debe entender primero, qué información demuestra valor,
qué necesita para decidir y cuál es el siguiente paso. No todas requieren hero,
features y pricing en ese orden. Para una aplicación: entrada/precondiciones,
decisiones/acciones, feedback/completado/recuperación y continuidad del contexto.
Define solo estados relevantes: vacío, loading, seleccionado, error, éxito,
restricciones o contenido largo cuando afectan la tarea.

Si la estructura es incierta, el agente puede proponer una composición simple,
wireframe, flujo o prototipo pequeño. Elige o retoma el medio antes de producirlo.
No necesita una biblioteca completa para explorar el funcionamiento. Un graybox
puede cerrar estructura y dejar totalmente abiertas tipografía, color e imágenes.
Si la estructura ya viene aceptada, no hace otro wireframe por cumplir el ritual.

Revisa: ¿qué entiende la persona?, ¿qué puede hacer?, ¿qué información necesita?,
¿qué sucede después?, ¿cómo vuelve o se recupera? Esto es decidir la experiencia,
no montar un proceso de QA. Referencias de patrones pueden ayudar de forma puntual;
no hay que buscar ocho galerías para resolver el comportamiento de un formulario.

SALIDA: estructura/contenido y recorrido suficientes para el alcance, con lo abierto
y lo aceptado claros. Puede quedarse en el mismo canvas o registro, sin documentos extra.

4. DEFINE LA DIRECCIÓN VISUAL

Explica las ideas que imaginas para ESA marca: carácter, jerarquía, tipo de imagen,
densidad, expresión y movimiento. Separa restricciones de ideas por explorar.
No necesitas conocer nombres de estilos. Si estás indeciso, pide opciones breves
fundamentadas en el producto; no cuatro sitios completos para decidir el tono.

El agente refleja tu intención y pregunta lo material. Una industria no obliga a
una estética; un ejemplo de este manual no es una preferencia tuya. Dirección
significa una idea que pueda expresarse en composición y relaciones visuales,
no simplemente decir "premium", elegir azul o copiar una marca famosa.

SALIDA: dirección confirmada y pregunta de búsqueda. Tú decides o delegas la elección.

5. REVISA REFERENCIAS Y DEFINE QUÉ TOMAR

Aporta links/capturas/moodboard o solicita búsqueda dentro de REFERENCES.md.
Las fuentes curadas se preservan. El agente escoge familias pertinentes y comienza
por fuentes útiles; no ejecuta todo el catálogo ni sale a galerías arbitrarias.
Se pueden agregar fuentes por decisión explícita tuya.

La revisión inicial usa ocho ejemplos claros por defecto, propios, encontrados
o combinados. Es un default de trabajo, no un número demostrado como óptimo.
Si no encuentra ocho que pueda inspeccionar y que encajen, te muestra el conjunto
válido y pide decidir entre otra búsqueda permitida, tus aportaciones o menos ejemplos.
No debe rellenar con referencias débiles ni fingir que abrió imágenes inaccesibles.

Por ejemplo debe mostrar link exacto, preview cuando sea posible, región útil,
relación observada, encaje, diferencia y límites. Abrir un original fuera del
catálogo requiere verificar el enlace desde la galería o que tú lo suministres.
Una captura muestra composición; no demuestra comportamiento oculto ni CSS exacto.

Tu trabajo: seleccionar y decir qué tomar. Puede ser escala/jerarquía de una,
relación tipográfica de otra, framing de otra y feedback de un patrón. No tienes
que mezclar ocho identidades. El agente sintetiza lo seleccionado y lo que evitar;
si hay instrucciones incompatibles, las aclara contigo en lugar de promediarlas.

SALIDA: mapa de contribuciones aceptado, no un montón de links almacenados.
Después solo se investiga la decisión abierta; no se repite la búsqueda completa.

6. ENTREGA FOUNDATIONS; DESARROLLA EL SISTEMA NECESARIO

Tu base puede ser un archivo, tokens, documento o diseño. Incluye tipografía y
roles, colores/roles semánticos, sizing, spacing/densidad, geometría y sombras
cuando importen. No todas las marcas necesitan efectos o todas las categorías.
Si falta una decisión, el agente pregunta u ofrece ayuda puntual para que la aceptes.

El agente desarrolla usos, aliases, derivados y reglas necesarios para las páginas
previstas. Distingue tus valores de sus propuestas y respeta rutas canónicas.
No crea cientos de tokens o dos sistemas que compitan. Muestra una aplicación
visual de las reglas, no solo una lista de variables. El vocabulario de diseño
necesita composición y experiencia para convertirse en una interfaz excelente.

SALIDA: foundations y reglas aceptadas para ESTE alcance.

7. DESARROLLA COMPONENTES Y PATRONES EN CONTEXTO

Acuerda inventario/batch si no existe. Se deriva de tareas y páginas reales,
no de cada control que tenga un framework. El agente desarrolla piezas pequeñas
con sus usos/estados y tú revisas la entrega antes de que la multiplique.
Después combina bases aceptadas en navegación, formularios, listados, paneles
y patrones que necesite el producto. El patrón resuelve la tarea y sus estados,
no solo un grupo mayor de rectángulos.

Revisa identidad, proporciones, densidad, tipografía, claridad y feedback con
contenido representativo. Los componentes deben reutilizarse de verdad donde
el medio lo soporte: instancias/bindings en canvas o componentes/tokens en código.
No es necesario construir toda biblioteca antes de componer una muestra para
ver cómo conviven. Si esa muestra revela un problema de base, revisa la corrección
propuesta y cambia solo lo que dependa de ella.

SALIDA: piezas/patrones aceptados y suficientes para componer, sin inventario futuro.

8. COMPÓN Y REFINA PÁGINAS HERMOSAS

Mantén un outline de página/flujo. El agente desarrolla el batch autorizado usando
la dirección, contribuciones de referencias, foundations y componentes aceptados.
La apertura debe tener un foco intencional; las regiones siguientes desarrollan
contenido, ritmo y densidad, en lugar de repetir el mismo formato de cards.

Juzga en el resultado real: relación dominante/soporte, type/image balance,
negative space, alineación óptica, wrapping, crops, color/superficies, consistencia,
profundidad de contenido, móvil y estados importantes. Movimiento se observa en
la secuencia, no solo en una captura. Un hero hermoso no termina la experiencia.

El agente debe identificar la carencia de mayor impacto antes de micro-polish.
Si el problema es de jerarquía, cambia esa relación; no agrega sombras para
simular una mejora. Si la idea o asset no sirven, propone una alternativa dentro
de lo delegado. Respeta lo cerrado y lo que ya funciona.

En cada iteración presenta una comparación útil: base -> propuesta, con contenido,
tamaño/estado y assets cargados comparables. Con trabajo nuevo, contrasta la
propuesta con el brief y relaciones elegidas de las referencias. Explica el aporte
visible y cualquier tradeoff. "Más premium", un score o pasar tests no prueba belleza.

Tu feedback: ubicación + relación que falla + qué conservar + efecto buscado.
Ejemplo hipotético: "La imagen perdió presencia respecto a la base. Conserva
el contenido y familia tipográfica; reequilibra título/imagen y muestra móvil".
Esto no impone esa estética en todos los proyectos.

Itera sobre el batch. Conserva una versión anterior si el supuesto polish la
debilita. No persigas efectos infinitos ni nuevas identidades por costumbre.
Acepta el resultado cuando la dirección y acabado que buscas aparezcan realmente;
esa aceptación desbloquea la expansión acordada, no todo el producto automáticamente.

Antes de presentarlas, el agente inspecciona fonts/crops, wrapping/clipping,
estados y tamaños relevantes; en un prototipo interactivo, comportamiento
aplicable. Corrige problemas materiales y repite solo lo afectado. Usa QA.md
por secciones pertinentes, sin otra entrevista o fase para ti. Una captura no
demuestra teclado, navegación real o producción; declara lo que no pudo observar.

SALIDA: páginas/experiencia aceptadas, con una contribución de diseño observable.

9. ENTREGA Y CONTINÚA SOLO LO QUE ELIJAS

El diseño puede terminar como canvas editable o visuales/prototipo legibles,
con fuentes canónicas, estados/intención responsive y decisiones de uso necesarias.
Después puedes pulirlo tú, seguir con AI o pedir código. El agente espera esa elección.
Una siguiente mejora comienza desde la base aceptada, no desde otra entrevista de marca.

Si pides implementación, se conserva el diseño: estructura, styles, componentes,
assets, estados y responsive. Reutiliza layout/prototipo útil, pero el código
provisional o mocked necesita adaptación a producción. No se debe convertir una
traducción a código en otro rediseño. El agente también se encarga de los checks técnicos pertinentes al código;
no te transfiere esa tarea ni los usa como prueba de calidad estética.

PENPOT Y OTROS MEDIOS

Usa tu medio existente o el elegido. Penpot es el canvas editable propuesto cuando
se comprueba conexión. El kit no activa su MCP por existir. Su documentación
revisada el 29/09/2026 describe opciones remota/local y MCP gratuito/abierto;
el cliente/modelo sigue consumiendo su suscripción y el cloud tiene límites de plan.

Para remoto: Account -> Integrations -> MCP Server, URL/key privadas de tu cuenta,
configuración soportada por tu cliente y File -> MCP Server -> Connect en el
archivo correcto. Mantén la pestaña conectada; el agente confirma archivo/página
y destino antes de editar. Credenciales no van al repo ni a las entregas.
Local solo si lo eliges y cumples sus requisitos; no se instala por defecto.

El agente consulta APIs reales, trabaja por operación lógica/region y devuelve
IDs/cambios útiles. Tras un error comprueba cambios parciales antes de repetir.
No reconstruye bibliotecas aceptadas ni devuelve el canvas entero por rutina.
Necesita vistas legibles para juzgar el diseño: un árbol JSON no demuestra belleza.
Si usas HTML/CSS, conserva ese trabajo útil cuando pases a código.

CÓMO AHORRAR SIN REDUCIR LA EXIGENCIA

No repitas contexto resuelto. Guarda decisiones y revisión/captura aceptada en
.design/project.md o el registro existente, separadas de propuestas pendientes.
No almacenes todos los resultados ni pegues todas las referencias cada turno.
No hagas una variante completa para resolver un detalle local. Corrige primero
lo que cambiará más la composición/experiencia; después el detalle fino.
No construyas un sistema para productos imaginarios. No abras varios workflows,
agentes o servicios por defecto. Más razonamiento no sustituye ver el resultado.
El esfuerzo y modelo que tú elijas mandan; compara consumo solo cuando sea observable.
