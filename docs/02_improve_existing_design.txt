IMPROVE AN EXISTING BASE — DESIGN KIT
Updated: October 5, 2026.

PROMPT IN THE AGENT INTERFACE
"Use Design Kit to improve [interface/region/flow] in this base.
Preserve [accepted decisions/content/system/behavior]. Open decision: [X].
Wanted vibe or actual problem: [Y]. Show the result and wait for my feedback.
Scope: [design / frontend with QA]."

Inspect the actual base, instructions, assets/tokens and accepted decisions.
Identify what already works and the highest-impact open gap.
Preserve source treatments the user values; distinguish later additions and
regressions from approved originals. Include the library shell when it is in scope.
Do not restart the whole design or rediscover galleries when evidence suffices.

Before visual edits, complete SKILL.md's comparison: intended visual source,
current discrepancy, proposed treatment and review scope. Inspect the source
and base separately; DESIGN.md or screenshots of the base alone do not suffice.
A density preference does not approve a diagnosis or global propagation.
If feedback rejects the diagnosis, reopen it before further dependent edits.
Investigate the named discrepancy; permission to continue does not approve a
diagnosis the user explicitly rejects. Show actual captures inline in chat when
requested; do not add product pages/routes solely to present review material.

Inspect the existing identity, canonical system sources and shared components.
Reuse explicit instructions about what to preserve/change. Local improvements
inside the existing vocabulary need no extra identity questionnaire. If the
request could change the identity/system and that boundary is unclear, show what
you found and ask a focused contextual question: preserve the relevant anchors,
evolve selected relationships, or replace within the requested scope. Free text
can specify what to retain. Resolve it in the existing context/vibe checkpoint.
Keep these decisions in this project, even when the skill is installed globally.

WHEN DIRECTION IS OPEN
Present the design MD's aesthetic as a hypothesis and ask a focused confirmation
before an exhaustive audit or treatment. Prior component approval does not settle
the whole identity. Reuse a vibe already supplied instead of asking it again.
Expand the user's wording into a faithful brief/prompt: requirements/negatives,
proposed interpretation and unknowns remain separate. Confirm the intended vibe.
Search by aesthetic in the selected MCPs; constrain the requested section/pattern
first when scoped. The business topic is an optional filter, not a requirement.
For exploratory evolution, use supplied examples to seed complementary MCP
research; reuse directly for faithful/local work or when accepted evidence covers
the decision. An example URL alone does not close an exploratory reference phase.
If MCPs lack usable evidence, try relevant catalog sources through browser/search.
If usable coverage is exhausted, describe the gap and invite user references.
Curate 4–8 strong, distinct, inspected initial references unless asked otherwise.
If fewer than four fit, continue eligible retrieval or report incomplete coverage
when actual access/budget is exhausted; do not pad or silently advance.
Show readable evidence, fit, transfer and exclusions for acceptance/correction.
After acceptance, ask whether to search further or continue with this selection;
reuse an explicit choice already given. Refine within eight active references.
Wait for the accepted map and search-closure choice.
A focused typography/composition repair does not need a full discovery round.

AFTER DISCOVERY CLOSES
Diagnose structural causes before cosmetic symptoms using DESIGN_DIRECTION.md.
Compare hierarchy, composition, grouping/task flow and shared system rules with
the accepted references. Explain how a cause produces the visible inconsistencies,
why a reference handles that relationship better and what transfers to this product.
Do not impose a layout redesign: repeated spacing/geometry drift may be the cause.
Inspect intrinsic padding, parent gaps/margins and container insets before deciding
where a spacing correction belongs; preserve source controls that already fit.
Separate demonstrated violations, accepted-intent mismatches and taste hypotheses;
do not assume a reference is correct or copy its surface treatment.
Review the scoped causal repair order, then fix shared causes canonically and
verify affected compositions through the existing system/UI checkpoints.
Show resolved/pending causes and the integrated baseline before optional polish.
Refinement adds useful reference principles after the structural repair; return
to a cause if new evidence reveals it. Preserve scope, semantics and accepted anchors.

WHEN FOUNDATIONS CHANGE
Inspect accepted originals beyond the home page: relevant public subpages,
component states, CSS/DOM and available published token/system sources.
Track coverage of needed rules. Deepen those sources first; if insufficient,
search focused supplements matching the missing pattern and confirmed aesthetic.
Show contribution/exclusions, review and replace rejected evidence, then resume
the affected decision. No new four-reference quota or whole-workflow restart.
Normalize accepted contributions into one coherent system and its protected anchors;
distinguish observed declarations/computed values from inferred/proposed tokens.
Reuse canonical tokens/components. Propose the minimum scoped correction supported
by accepted evidence, render its specimen and obtain review.
Revise affected canonical design MDs with the accepted reference-to-product rules;
keep documentation and the rendered system/UI consistent without duplicating APIs.
Inspect affected shared consumers and show the relevant impact before propagation.
Do not create a competing system or claim complete extraction of another site's
internal system from public styles/screenshots.

WHEN THE INTERFACE CHANGES
Develop one coherent treatment within the requested scope.
Compare before/after with equivalent content, state, viewport and loaded assets.
Inspect the integrated result; an isolated attractive card or hero is insufficient
evidence for a whole-interface claim. Explain the visible contribution.
Correct and show again. Preserve a stronger earlier result if polishing weakens it.
A section request remains that section; later sections reuse its accepted choices.

FRONTEND AND QA
Implement when frontend is already requested or requested later.
Preserve accepted visual decisions while integrating existing behavior/API contracts.
Verify relevant states, widths, loaded assets, keyboard/focus and target checks.
Label mocks and untested services. Backend remains outside the kit.

RESUME
"Continue with Design Kit from [artifact/revision]. Accepted: [X].
Pending: [corrections]. Preserve the rest and show the affected revision."
Reread mutable work/human edits; paths alone do not prove acceptance.
Invalidate only affected dependent work rather than the whole product.

Reuse retrieved schemas/results/captures; repeat discovery only for an actual
changed direction or evidence gap. Respect provider limits and user budgets.
HOSTS.md covers the three platforms/interfaces; PROVIDERS.md covers reference
access/efficiency. SKILL.md/ONBOARDING.md are the procedure. TASTE.md and
DESIGN_DIRECTION.md guide judgment; QA does not establish beauty.
