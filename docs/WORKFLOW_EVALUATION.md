# Behavioral regression trials

Maintenance/evaluation guidance, not routine design context or a second workflow. Use SKILL.md as the procedure. Package and protocol tests cannot show that an agent followed it.

## Run and assess

Use a separate disposable target with its own raw screenshots, sources and instructions. Keep the model/settings, starting artifacts and budget fixed when comparing kit revisions or a no-kit baseline. Start from the actual user request below, not a prompt containing the expected answer. Supply only the scenario's raw inputs. Review the real action trace, viewed visuals, proposed changes and human responses, not a summary declaring compliance. Do not edit a live product or purchase model/provider access to run these cases without authorization.

Record `kit revision; host/model; scenario; first proposed action; inspected sources/captures; actual queries/errors/fallback; human review and scope; first edits; outcome`. An absent required tool/view/review is **not tested**, not a pass. A claimed visual comparison without opened evidence is a failure. Keep results in the evaluation target; never import its identity into the kit. No numerical taste score is required.

| Case | Initial request and raw inputs | Observable pass criterion |
| --- | --- | --- |
| Existing library, open visual quality | "Improve this UI library. Its structure is acceptable, but its controls and marks should match our existing products." Provide the library captures, design document, product captures and original assets. | Inspect the product targets separately from the library. Present an evidenced discrepancy and scoped treatment before visual edits. Structure acceptance does not close the visual diagnosis. No substitute audit of only widths/overflow. |
| Existing MD, unconfirmed intended aesthetic | "Improve the whole UI using the identity we want." Provide an existing design MD, representative base views and an accepted small component batch, but no human confirmation of the overall direction. | Inventory relevant sources; present the MD's aesthetic reading as a hypothesis and ask a focused confirmation/correction before an exhaustive audit or treatment. Do not declare the full identity closed from prose or the accepted component batch. Identify material documentation gaps. |
| Answer already supplies the vibe | Reply to the direction question with a specific aesthetic, desired evolution and an example URL. | Incorporate that answer and inspect the example. Do not repeat the same open-ended vibe question or wait on the stale question. Clarify only an unresolved transfer choice. |
| Exploratory example, further research | "Use this example as inspiration for evolving our existing UI; find complementary references and adapt them to our product." Supply one visual example and available reference MCPs. | Use the example to form aesthetic/pattern queries; actually retrieve and inspect complementary references before foundations. Present transfer/exclusions rather than copying the example, assuming it is a complete direction, or asking whether to perform the already requested research. |
| Too few strong references | Request exploratory discovery with a confirmed vibe. Initial results include two strong matches and several weak or duplicate ones; another eligible source is available. | Continue purposeful retrieval until 4–8 distinct inspected references qualify. Do not count weak matches, duplicate crops or unopened links. If actual access/budget is exhausted, report an incomplete selection and request evidence/refinement rather than advancing. |
| Reference checkpoint, refine or advance | Show a qualifying selection. First respond "These fit"; when asked about further discovery, request closer examples. After revision respond "These fit; use them and continue." | After acceptance, ask the missing further-search/continue choice. Keep discovery open for refinement and reuse evidence with at most eight active references. Advance after the explicit final choice without asking it twice. |
| Structural cause versus cosmetic symptoms | "Improve this interface using the accepted references; no more research." Provide current views with competing action priorities, fragmented grouping and repeated component inconsistencies, canonical sources and reference views showing clearer relationships. | Before editing, explain evidenced causes, why relevant reference relationships work, product-specific repairs and affected scope. Review the repair order; fix hierarchy/grouping/shared rules before optional micro-polish and verify integrated consumers. A list of radius/spacing tweaks without a causal diagnosis fails. |
| Reference quality versus evidence | Supply an accepted aesthetic example whose relevant control state has the same issue as the current UI, plus a deliberate product-specific difference and an unobserved interaction. | Check the relevant region/state instead of treating the reference as infallible. Exclude unsupported contributions, preserve intentional differences and label unobserved behavior. Separate demonstrated defects from aesthetic hypotheses; do not invent an objective quality verdict. |
| Accepted evolution, outdated design prose | Accept a reference-to-product map and request improvement of the existing system, design MDs and UI. Provide tokens/component APIs and a design document that lacks these relationships. | Review scoped system/document changes together; turn accepted relationships into usage rules, preserve canonical APIs/values unless a change is reviewed, and reconcile affected MDs with the rendered treatment. Neither documentation-only editing nor UI-only editing completes the request. |
| Selected original, deeper evidence | "Develop the system from these accepted references." Supply an accepted home preview, an accessible original with detail/form routes and a public stylesheet whose declarations differ at breakpoints. | Map and inspect relevant routes/states beyond the home page, reuse repeated-template evidence and inspect actual available styles. Retain route/state/viewport provenance; distinguish declared/computed values from inferred tokens and do not claim the full internal system. |
| System coverage gap, supplemental loop | Accept the initial direction and start system work. Provide strong composition evidence but no relevant form/error-state evidence; make an eligible matching source available. Reject its first proposed contribution, then accept a revised one. | Deepen accepted sources first, identify the missing pattern plus agreed aesthetic, retrieve and review focused supplements. Revise the rejected contribution before dependent implementation, preserve unaffected approvals and resume the current phase. No forced four new references or whole-workflow restart. |
| Conflicting reference systems | Supply accepted references with compatible overall tone but conflicting typography/geometry rules, protected product anchors and existing canonical tokens. | Identify the conflict, propose normalized product-specific roles/rules within the confirmed aesthetic and review consequential choices in a rendered specimen. Verify consistent repeated roles/states across consumers; do not combine each source's raw system or silently replace anchors. |
| Craft improvement without identity copying | "Use these references to improve our own aesthetic. Their texture and depth are examples, not requirements." Supply a structurally sound base, protected identity and references with stronger layering/material treatment but a different brand palette/type. | Explain the source achievement, current opportunity, transferable mechanism and target-specific treatment. Show the benefit/tradeoffs in the actual reviewed result. Neither clone the source identity nor add every effect by checklist; do not reduce the assignment to bug fixes or reject useful finish solely as decoration. |
| Narrow answer | At the proposed treatment checkpoint, answer only "I prefer denser layouts." | Record a density preference; do not infer acceptance of the diagnosis, an unseen specimen or changes to global defaults. Resolve the remaining review with the current artifacts. |
| Rejected interpretation | After the first proposal: "That is not the problem. The selection controls and marks are off; the popover already works. You may keep working, but your diagnosis is wrong." | Stop dependent edits under the old diagnosis, inspect the named discrepancies and show the corrected interpretation. Permission to work does not approve the rejected premise. Preserve the popover and unrelated accepted work; no global propagation under that premise. |
| Valued source, inconsistent additions | "I like the original product controls. Improve the additions and this library's own UI; the button spacing is wrong." Provide source/current views and component/container code with a correct source control but inconsistent parent gaps and later component rules. | Preserve the valued source treatment, trace derivative/addition mismatches and inspect the scoped library shell. Distinguish intrinsic padding from parent spacing and repair the evidenced owning rule. Do not redesign approved originals or substitute an unsupported navigation/density diagnosis. |
| Chat-only review evidence | "Show the comparison as images in chat; do not add pages to the app." Provide an existing running preview and source/current views. | Show real captures with useful states/viewport provenance. No presentation-only route, navigation entry or comparison component in production. If isolation is needed, use a disposable external artifact and remove only owned temporary material. Generated mockups cannot stand in for render verification. |
| Requested MCP, host failure | "Use the connected reference MCP to find matching examples." Provide a visible tool that returns a protocol error and an available public-catalog route. | Actually call the relevant tool. Report its failure as an access issue; use and visually inspect eligible fallback evidence. Do not say the catalog is empty or label a direct endpoint diagnostic as native success. |
| Hero, aesthetic across industries | "Improve only this hero: technical but human, approachable rather than cold." Provide surrounding context, a protected palette/font and working website-reference tools. | Search the requested pattern and observable aesthetic. Do not automatically constrain to the business genre or redesign the whole site. Show contribution/exclusions and review only required foundations. |
| Supplied evidence suffices | "Match this accepted control treatment; use these screenshots, no extra gallery research." Provide readable source/current captures and existing component APIs. | Reuse the supplied evidence, compare the exact state and preserve semantics. No compulsory MCP search, full design-system rebuild or repeated identity questionnaire. |
| Real component API versus prose | "Add this state to our existing component." Provide DESIGN.md, tokens, component source/API and a conflicting illustrative prose example. | Consult the existing API and canonical values, resolve material conflict, reuse the component and show the scoped state. Do not generate a parallel primitive from prose or copy the whole API into DESIGN.md. |
| Visually changed selection control | "Use this square selection treatment." Provide a mutually exclusive group and a reference showing square indicators. | Adapt the visual treatment while retaining radio-group keyboard/selection semantics unless behavior is explicitly changed. Show checked, unchecked and focus states. |

## Current evidence

The supplied existing-library conversations are failure traces for comparison, priority, approval scope, confirmation of intended aesthetics and correction handling. The 4–8 selection and advance/refine checkpoint are explicit user requirements, not empirical quality thresholds. These cases are not successful trials of the updated kit. Later native checks in this desktop chat returned images and links from both Awwwards and One Page Love after the Codex compatibility adapter was installed and reloaded. A provider's missing optional capture dependency can use an existing browser; this does not excuse skipped direction/reference reviews. Offline diagnostic tests exercise protocol/result/error handling; they do not invoke an LLM. No post-update independent model trial or measured visual uplift is claimed here.
