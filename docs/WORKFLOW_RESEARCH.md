## Independent selection and theoretical checks

Official [OpenAI evaluation guidance](https://developers.openai.com/api/docs/guides/evaluation-best-practices) supports task-specific criteria, comparisons and expert calibration, rather than a generic positive verdict. [W3C evaluation guidance](https://www.w3.org/WAI/test-evaluate/) and [tool-selection guidance](https://www.w3.org/WAI/test-evaluate/tools/selecting/) explicitly require human/manual evaluation for checks tools cannot automate. These independently support precise comparisons and partial-audit reporting; they do not validate a synthetic persona as an actual user.

For each candidate practice, ask: what failure does it address, what evidence supports the mechanism, when does it apply, what extra work does it cost, and what result remains unproven? Retain a practice only if it changes a decision, implementation or meaningful check. Theoretical edge-case review produced these rules:

| Situation | Selected action | Unnecessary cost or failure avoided |
| --- | --- | --- |
| Original expressive site with no direction | Relevant exceptional references, product-derived premise, a representative screen plus deeper region and mobile; inspect/repair the concrete craft gap | Vague premium adjectives, a beautiful isolated hero, repeated complete variants before resolving the idea |
| Dense app or plugin, same high craft ambition | Precise task hierarchy, expressive choices compatible with use and host, actual states and strong appropriate product examples | Importing a campaign's scrolling spectacle, removing useful data to appear minimal or postponing engineering constraints |
| User's structural base with unfinished finish | Preserve closed structure, resolve delegated finish, compare equivalent renders; explore a widget only if that region remains uncertain | Reopening identity, copying placeholder styling or recreating the whole page |
| User's final design or accepted system | Faithful implementation/extension, real component bindings and targeted checks | Unrequested discovery, extra mockups and competing systems |
| Small code edit or reproducible bug | Repository evidence, cause-specific repair, meaningful targeted checks and diff | New specification framework, excessive tests, factory infrastructure or broad unrelated refactor |
| Coupled feature or sensitive boundary | Outcome/boundary/evidence map, early uncertain integration, complete capability and risk-based negative/recovery checks | Treating mocked success or an agent's summary as production proof |
| Repeated failure or long work | New hypothesis/evidence; narrow verified knowledge and recoverable handoff | Repeated same prompt, indiscriminate effort escalation, stale memory and whole-history replay |

This comparison supports the three workflows as current, defensible operating recommendations for the stated objective. The expected efficiency benefit is a causal hypothesis: reduce uncertain invention, duplication and later rework while preserving the requested quality. It does not establish a numerical Sol benefit, universal optimum, subscription duration or guaranteed exceptional artifact. The user explicitly chose theoretical research now and personal practical testing later; application trials are not a delivery gate for this request.

### Failed prior runbook supplied by the user

The six-page `High_End_AI_Software_FINAL_RESULTS_WORKFLOW (2).pdf` was read and rendered. The user reports that it added structure without improving outcomes; this is evidence about their experience, not a controlled diagnosis of a particular model. Keep its useful mechanisms: a compact outcome contract, actual early render, smallest justified repair, preservation of stronger work and checks appropriate to concept/prototype/production. The new guide does not inherit its authority or paste its master prompt into every task.

Its unresolved weaknesses include the uncalibrated “7–8+” first-handoff target, assumed taste-pack/starter availability, broad requests to co-invent identity/asset/motion, a fixed two-to-three issue batch, and wording that places engineering after visual freeze. These can leave important decisions ungrounded or add work; they do not prove the cause of every failed result. Replace them with available inspected references and product-specific criteria, named mismatches, conditional assets/motion, scope-driven repair batches and early boundary/host checks. Same-agent self-refinement is useful but is not independent review. No new folder hierarchy, mandatory evaluator, freeze ceremony or recurring documentation is required.

The human guide presents exactly three task workflows: design from scratch, iterate on the user's design base, and programming. Shared cost/evidence rules support them; conditional canvas/release/bug handling does not become another universal workflow.

Package checks establish packaging only. No actual application-generation experiment was run in this maintenance task, in accordance with the user's explicit preference. An LLM reviewing these instructions is also not a product outcome evaluation. The following protocol is optional future validation, not a required task now.

Use recoverable target snapshots for a small representative set: open visual direction, faithful design implementation, existing-system extension, a persistent feature with recovery, a reproducible bug and a sensitive boundary if relevant. Write prompts, acceptance checks and comparison criteria before running. Pin kit revision, initial code, available tools, task/model/effort and budget. Keep all conditions equivalent except the workflow being compared; record supplied references versus references discovered during the run. Compare task completion and failure paths first, then product fit, visual coherence/craft and maintainability; do not compensate for a broken must-pass outcome with a high beauty score.

Inspect same viewport/state/content/loaded assets. Where feasible, show anonymized A/B results to the user without labeling the kit version; a calibrated reviewer may assist, but cannot certify quality. Keep the actual artifacts and reproduction steps, not just a score. Record elapsed time, repair cycles, accepted result and measured usage where exposed; missing quota/token measurements remain unknown. One run is exploratory, not a universal gain. Repeat only enough to resolve a useful uncertainty within the authorized budget; automated model runs and extra reviewers need their own available authorization.

For behavioral regressions, check trace/artifacts for skill activation, respected closed design, applied-reference evidence, actual render inspection, required outcome checks and honest handoff. Prefer outcomes over exact wording, file counts or a fixed command sequence. Add a case after a real failure. Retain a control without the kit or the previous revision when measuring incremental benefit; compare multiple cases before generalizing.
