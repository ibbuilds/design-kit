# Make the visual treatment earn its place

Use for an unresolved design choice under [SKILL.md](SKILL.md). This is a decision aid, not an additional phase or a demand for another document. Apply only what the current complaint needs.

## Work at the right level

Classify the actual gap before choosing the intervention:

| Observed gap | Useful intervention |
| --- | --- |
| Derived controls no longer resemble valued originals | Reuse the accepted implementation; trace changed padding, type, icon, border or state owners. |
| Correct tokens but incoherent composition | Compare attention order, relative scale, effective whitespace, enclosure and asset weight in context. |
| Weak visual premise or generic structure | Choose a stronger product-specific composition or type/image relationship inside the delegated scope. |
| Good treatment, poor execution | Correct implementation drift rather than reopening identity. |
| Good isolated specimen, weak consumers | Adjust the shared relationship and its usage together; inspect meaningful exceptions. |
| Missing necessary asset or fidelity source | Resolve that concrete gap; do not substitute a decorative approximation and claim a match. |

This classification is a hypothesis, not a verdict. Inspect source/current views and relevant properties. If feedback rejects it, investigate the named issue instead of defending the prior explanation. A controls complaint does not automatically call for navigation or density redesign.

## Select a coherent improvement

Identify what the user values, what currently limits quality, and which change could make the largest relevant visible difference. Consider both defect repair and positive design opportunity. A functional page can still need stronger identity, typography, imagery, rhythm or composition.

Write only the useful working relationship: **gap/opportunity -> mechanism -> expected visible difference -> protected anchors**. Keep it in existing notes. Usually one to three coordinated moves are enough to focus the candidate; a family-wide spacing repair can be one move across many consumers. This is not an arbitrary limit on required scope.

Use an accepted in-product example or inspected reference as a quality anchor when available. Examine the relevant region at a comparable viewing scale; distinguish real source observations from inferred design choices. Do not invent ratios, font identities, internal tokens, interaction behavior or conversion evidence from a screenshot.

Select a dominant treatment instead of averaging every reference. Adapt relationships to this product's content, density and constraints; do not copy another identity or treat every source decision as correct. One reference can answer one question without resolving the entire system. When outside evidence cannot answer an open choice, make an explicitly agent-authored proposal if the scope permits it.

No universal palette, radius, spacing grid, font, card ban or effect quota belongs here. A visual vocabulary constrains repetition, not every composition. Texture, depth and motion may contribute when they serve the intended treatment; their addition is not itself improvement. Preserve required grids and approved exceptions rather than inventing a new system.

## Make the candidate persuasive in context

Use real content, loaded fonts, correct assets and representative states. Compare the whole composition before zooming into a detail. For a family, examine related controls together and in a consumer. For a screen, include a state or container that challenges the initial treatment.

Develop affected type/color roles, spacing and components inside that composition using [CRAFT.md](CRAFT.md). Prefer existing canonical implementations; change their owner when it explains repeated symptoms. Inspect actual effective values and inherited styles rather than compensating for unknown causes with local overrides.

Keep code as the source of the chosen visual values. Do not first require a prose specification detailed enough to recreate the design. If a separate worker is already authorized, hand off the accepted implementation and captures rather than asking it to reinterpret aesthetic adjectives. The kit does not require a second model.

## Judge the result, not the explanation

Compare baseline and candidate at equivalent content/state/viewport and loaded assets, then compare the quality anchor's relevant relationships. Review the images before using your own rationale as evidence. Ask:

- Is the intended visual contribution actually visible at normal viewing size?
- Does the result hold together across the changed family/composition, or did a local win weaken something else?
- Does it meet the user's requested quality bar, rather than only being less inconsistent than before?

A better baseline is a relative gain, not automatic acceptance. A checklist pass is not visual uplift. Preserve stronger earlier work. Report tradeoffs and distinguish observed improvement from unverified usability or business outcomes. Do not assign a numerical self-score.

Within SKILL.md's remaining budget, correct execution drift or replace a weak local hypothesis. Do not add unrelated embellishments because the prompt asks for excellence. If another pass gives no material gain, stop repeating it; report the unresolved treatment/evidence problem. Human acceptance remains distinct from the agent's recommendation.

After acceptance, reuse actual code, assets and relationships. Verify a contrasting consumer before claiming a shared treatment generalizes. A whole-library task retains coverage of affected families, states and exceptions; one successful screenshot does not close the rest.
